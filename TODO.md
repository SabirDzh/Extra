## Контекст проекта

В репозитории есть backend на FastAPI, SQLAlchemy и Alembic. Отдельного frontend-кода в проекте нет, поэтому переходы назад и остальные требования проверяются через API-контракт, которым пользуется фронтенд.

## Результаты аудита

### 1. Тесты, прогресс курса и сертификаты

Найдено несколько мест, где тестовый блок может засчитываться неправильно:

- `backend/Repository/test_grading.py` помечает автоматический тест пройденным независимо от результата, потому что проверяется сам тип блока.
- В ручной проверке администратора блок засчитывается при результате `> 0`, а не только при 100%.
- Прогресс курса и выдача сертификата опираются на флаги `UserBlockProgress.is_completed`, не проверяя, был ли тест реально сдан на 100%.
- Из-за этого старый или ошибочно установленный флаг может привести к завершению курса и выдаче сертификата.
- В результатах теста есть потенциальная несогласованность: в одних местах используется полное количество вопросов, а в других учитывается лимит `questions_count`.

Требуемое бизнес-правило:

- Курс считается пройденным на 100% только тогда, когда каждый его блок пройден на 100%.
- Тестовый блок считается пройденным только при результате ровно 100%.
- Если хотя бы один блок, включая тестовый, не пройден на 100%, курс не считается завершённым.
- Сертификат можно выдавать только после прохождения всех блоков курса на 100%.
- Непройденный тест не должен учитываться в прогрессе курса.
- Правило должно одинаково использоваться в grading, progress, course completion, test results, profile и certificates.

### 2. Переход к ранее пройденным этапам

Сейчас API возвращает:

- `blocks` — текущий доступный этап;
- `completed_blocks` — предыдущие завершённые блоки;
- `current_block_id`;
- `next_block_id` у каждого блока.

Проблемы API-контракта для фронтенда:

- отсутствует `previous_block_id`;
- отсутствует единый упорядоченный список всех доступных пользователю блоков;
- `blocks` и `completed_blocks` разделены, поэтому фронтенду приходится самостоятельно объединять их;
- `next_block_id` может указывать на следующий блок, который ещё недоступен;
- прямой `GET /courses/{course_id}/blocks/{block_id}` не проверяет, заблокирован ли этап;
- если после успешной попытки пользователь отправляет неудачную, `UserBlockProgress` может остаться пройденным, а логика последней попытки одновременно считать этап непройденным. В ответе появляются противоречивые данные.

Предлагаемое исправление:

- возвращать для каждого блока явные признаки `is_completed` и `is_unlocked`;
- добавить `previous_block_id` и корректный `next_block_id`;
- предоставить фронтенду единый упорядоченный список доступных блоков либо однозначно описать связь между `blocks` и `completed_blocks`;
- оставить ранее пройденные этапы доступными для повторного просмотра;
- открывать следующий незавершённый этап только после прохождения текущего на 100%;
- запрещать открытие заблокированных этапов прямым запросом;
- исключить противоречия между `UserBlockProgress` и последней попыткой теста.

### 3. FAQ

Текущая модель `FAQ` содержит только:

- вопрос;
- ответ;
- порядок отображения;
- признак публикации.

Темы отсутствуют. В миграциях есть создание таблицы `faqs`, но начальных вопросов в коде и seed-файлах нет.

Локальная база `backend/test_db.sqlite` не содержит таблиц или записей FAQ. Содержимое production PostgreSQL из репозитория проверить нельзя, поэтому наличие вопросов на сервере нужно будет проверить подключением к целевой базе или во время миграции.

Требуемое решение:

- добавить сущность `FAQTopic`;
- связать каждый FAQ с темой;
- создать набор тематик по фактическому содержимому вопросов;
- реализовать идемпотентный алгоритм распределения вопросов по темам;
- запускать алгоритм при миграции на сервере, чтобы существующие вопросы автоматически получили темы;
- использовать тот же алгоритм при создании, изменении и импорте новых FAQ;
- сгруппировать FAQ в API-ответе или предоставить данные, достаточные фронтенду для группировки по темам.

Предлагаемый алгоритм автоматического распределения:

1. Нормализовать вопрос и ответ: привести к нижнему регистру, убрать лишние символы и привести текст к сопоставимому виду.
2. Для каждой темы задать список ключевых слов и фраз.
3. Посчитать совпадения в вопросе и ответе с разными весами.
4. Назначить тему с наибольшим результатом.
5. При недостаточной уверенности отправлять вопрос в тему `Общие вопросы`.
6. При одинаковом результате использовать фиксированный приоритет тем, чтобы распределение было стабильным.

Алгоритм должен быть детерминированным и безопасным для повторного запуска при каждом деплое: он не должен создавать дубликаты тем, а распределение вопросов должно оставаться предсказуемым.

### 4. Фильтрация обучения по роли пользователя

Сейчас поле `Course.audience` поддерживается, но автоматической фильтрации по роли пользователя нет:

- без параметра `audience` список возвращает все опубликованные курсы;
- фильтр `audience=installer` возвращает только курсы монтажника, а не курсы для всех;
- получение курса, запись на курс и доступ к блокам не проверяют соответствие аудитории;
- роль `buyer` есть в enum курса, но текущая проверка доступа к курсам покупателей не включает.

Требуемое правило для обычного пользователя:

```text
Course.audience IN (everyone, current_user.role)
```

Пример: монтажник должен видеть курсы для всех и курсы для монтажников, но не курсы для продавцов или сервисников.

Правило нужно применить к:

- списку курсов;
- поиску курсов;
- получению курса по идентификатору;
- записи на курс;
- доступу к блокам курса;
- связанным операциям, где пользователь может получить данные курса.

Администратор должен иметь доступ ко всем курсам.

## Допущение по повторной сдаче теста

Предлагаемая логика повторной сдачи:

- тестовый блок считается пройденным, если у пользователя есть успешная попытка на 100%;
- последующая неудачная попытка не должна автоматически аннулировать уже полученное прохождение;
- неудачная попытка сама по себе никогда не должна устанавливать прохождение.

Это допущение необходимо подтвердить перед реализацией.
