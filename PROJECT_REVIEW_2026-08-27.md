## P0 — исправить немедленно

### P0-1. Панель SQLAdmin доступна без какой-либо аутентификации

**Где:** `backend/create_fastapi_app.py:92-96`, `backend/admin/__init__.py:7-9`, `backend/admin/user.py`, `backend/admin/access_token.py`.

`Admin(...)` создаётся без `authentication_backend`, а SQLAdmin при его отсутствии намеренно пропускает проверку (`sqladmin/authentication.py`, декоратор `login_required`). Панель смонтирована по умолчанию на `/admin`. В ней зарегистрированы редактируемая модель пользователей и модель access tokens. Список токенов прямо включает `AccessToken.token`; у пользователя в форме не исключены роль, статус и хэш пароля.

**Последствие:** любой посетитель может открыть административную панель, читать пользователей и токены и, с настройками ModelView по умолчанию, менять или создавать записи. Это даёт захват учётных записей и данных.

**Что сделать:** до следующего развёртывания отключить mount `/admin` либо подключить `AuthenticationBackend`, который допускает только активного пользователя с `UserRole.admin`. Не отображать и не редактировать access token и `hashed_password` через UI. После закрытия доступа отозвать все существующие access tokens и проверить audit-логи.

### P0-2. Пользователь сам назначает себе роль администратора через `PATCH /users/me`

**Где:** `backend/core/schemas/user.py:60-64`, `backend/api/api_v1/users.py:215-220`, пакет `fastapi_users/router/users.py:87-96`, `backend/api/dependencies/authorization.py:8-15`.

`UserUpdate` содержит поле `role`. Стандартный маршрут FastAPI Users принимает эту схему для `PATCH /api/v1/users/me`. Его «безопасный» режим отбрасывает только `is_superuser`, `is_active`, `is_verified` и несколько системных полей; пользовательское `role` в исключениях отсутствует. Проверка `current_admin` доверяет именно `current_user.role`, а не `is_superuser`.

**Воспроизведение:** авторизованный покупатель отправляет `PATCH /api/v1/users/me` с телом `{"role":"administrator"}` (или поддерживаемым эквивалентом роли), затем обращается к любому маршруту с `current_admin`.

**Последствие:** полная эскалация прав обычного пользователя до администратора API.

**Что сделать:** удалить `role` из схемы self-update; оставить отдельную схему для администратора на маршруте `/{user_id}/permissions`. Дополнительно переопределить `UserManager.update` с явным allow-list полей для self-update как защиту в глубину. Добавить регрессионный тест: изменение `role` и `is_superuser` через `/me` возвращает 4xx и не меняет запись в БД.

## P1 — высокий приоритет

### P1-1. Сброс пароля немедленно меняет пароль и отправляет новый пароль открытым текстом

**Где:** `backend/core/authentication/user_manager.py:86-105`, `backend/api/api_v1/auth.py:42-44`, `backend/mailing/send_password_reset_email.py:14-18, 38-41`.

Обработчик `on_after_forgot_password` генерирует пароль, сразу сохраняет его хэш и отправляет сам пароль по email. Переданный FastAPI Users reset token при этом не используется для подтверждения смены.

**Последствие:** любой, кто знает email пользователя, может многократно вызвать «забыли пароль» и немедленно лишать владельца доступа (DoS). Пароль оказывается в почтовом ящике и может сохраниться в логах/архивах почты.

**Что сделать:** ввести проверку пользователя, который вводит данные для сброса пароля для почты, если это сам пользователь, то позволять, если это сторонний пользоветель, отклонять 

### P1-2. Docker-образ не содержит `pg_dump`, поэтому бэкапы в контейнере не работают

**Где:** `backend/Dockerfile:39-45`, `backend/scripts/backup.py:35-38`, `backend/api/api_v1/backups.py:12-19`.

Runtime-stage устанавливает только `libpq5` и `curl`; бинарника `pg_dump` там нет. При этом ручной endpoint и планировщик вызывают `subprocess.run(["pg_dump", ...])`.

**Последствие:** создание бэкапов в опубликованном образе завершается ошибкой. Endpoint возвращает наружу текст исключения, который может содержать строку подключения к БД.

**Что сделать:** установить в runtime-stage совместимый `postgresql-client`, добавить smoke-test контейнера с `pg_dump --version`, вернуть клиенту обобщённую ошибку, а подробности оставить в серверном логе без DSN.

### P1-3. Генерация сертификатов PDF ненадёжна и блокирует обработчик запроса

**Где:** `backend/Dockerfile:29, 47, 52`, `backend/core/certificate_pdf.py:23-39`, `backend/api/api_v1/certificates.py:105-132`.

Chromium устанавливается в builder-stage, но в runtime копируется лишь `/app/.venv`; стандартный кэш браузеров Playwright туда не попадает. При первой неудаче endpoint синхронно запускает `playwright install chromium` внутри async-функции. У операции нет таймаутов, а runtime-stage также не устанавливает зависимости браузера.

**Последствие:** скачивание сертификата может зависать или падать в production; один запрос блокирует event loop. В этой рабочей среде сценарий PDF не завершился более 90 секунд.

**Что сделать:** собрать браузер и его системные зависимости в runtime-образе, убрать установку браузера из request path, задать строгие таймауты и ограничение параллелизма. Для масштаба генерировать/кешировать PDF в фоне.

### P1-4. Статические маршруты продуктов недостижимы из-за порядка регистрации

**Где:** `backend/api/api_v1/product.py:240-267, 376-380, 392-395`.

`GET /{product_id}` зарегистрирован раньше `GET /summary/` и `GET /popular/`. FastAPI сопоставляет маршруты по порядку: `summary` и `popular` попадают в UUID-параметр и возвращают 422, а не вызывают нужный обработчик.

**Что сделать:** перенести `/summary/` и `/popular/` выше `/{product_id}`. Добавить endpoint-тесты, ожидающие 200 для обоих адресов.

### P1-5. Секреты из `backend/.env` могут попасть в Docker image

**Где:** отсутствует `.dockerignore`; `backend/Dockerfile:52`; `.gitignore` не влияет на Docker build context.

Docker собирается с корневым context и выполняет `COPY backend/ .`. Локальный `backend/.env` существует и игнорируется Git, но без `.dockerignore` будет включён в образ при локальной/серверной сборке, если находится в context.

**Последствие:** секреты БД, ключи токенов и настройки почты могут оказаться в слоях образа и в registry.

**Что сделать:** добавить `.dockerignore` с `backend/.env`, `.env`, `backups`, `media`, `.venv`, тестовыми артефактами и локальными файлами. Передавать конфигурацию только при запуске контейнера через secret manager/environment. Проверить уже опубликованные образы и ротировать секреты, если образ собирался рядом с `.env`.

## P2 — средний приоритет

### P2-1. Неограниченный глобальный счётчик путей позволяет исчерпать память

**Где:** `backend/middlewares/requests_count_middleware.py:17-38`.

Глобальный `defaultdict` хранит счётчик для каждого сырого `request.url.path` и никогда не очищается. Любой внешний клиент может послать неограниченное число запросов к уникальным 404-путям (`/x/<случайная-строка>`), создавая новые ключи в памяти каждого worker.

**Последствие:** постепенный memory leak и доступная извне DoS-атака.

**Что сделать:** считать по шаблону маршрута, а не по сырому URL, ввести allow-list/лимит кардинальности и TTL. Не хранить неограниченную метрику в памяти приложения.

### P2-2. Планировщик и бэкапы блокируют приложение и дублируются при масштабировании

**Где:** `backend/create_fastapi_app.py:27-43`, `backend/core/scheduler.py:8-47`, `backend/scripts/backup.py:12-69`.

Каждый экземпляр приложения безусловно запускает локальный `AsyncIOScheduler`, а его jobs вызывают синхронные `pg_dump`, создание tar-архива и операции с файлами. При нескольких workers/replicas каждый создаст собственные еженедельные и ежемесячные бэкапы; работа блокирует event loop.

**Последствие:** дубли бэкапов, гонки ротации, нагрузка на БД и подвисание API во время архивации.

**Что сделать:** вынести расписание в отдельный worker/cron/job scheduler с единственным лидером или распределённой блокировкой. Выполнять работу вне event loop и добавить мониторинг/алерт на успешность бэкапов.

### P2-3. Администратор может скачать произвольный читаемый файл через backup download

**Где:** `backend/api/api_v1/backups.py:40-51`.

Путь строится как `BACKUPS_DIR / filename`, после чего проверяется только существование и то, что объект является файлом. Нет проверки `resolve()` на принадлежность `BACKUPS_DIR` и нет allow-list имени архива.

**Последствие:** пользователь с ролью admin может запросить путь с `../` и получить любой читаемый приложением файл (включая конфигурацию). Это не внешний unauthenticated-доступ, но критично при компрометации админской сессии и усиливает P0-2.

**Что сделать:** принимать только имя из списка, который возвращает `list_backups`, и дополнительно проверять `candidate.resolve().is_relative_to(BACKUPS_DIR.resolve())`; требовать шаблон `backup_*.tar.gz`.



### P2-5. Загрузка схемы продукта принимает файл любого типа и размера в память

**Где:** `backend/api/api_v1/product.py:294-319`, `backend/create_fastapi_app.py:86-90`.

Endpoint для admin берёт расширение из имени, целиком читает upload в память и публично публикует его под `/media` без проверки размера, MIME или содержимого. Можно загрузить HTML/SVG/скриптоподобный контент или очень большой файл.

**Последствие:** расход памяти/диска и stored XSS на домене приложения при компрометации админа или ошибочном использовании панели.

**Что сделать:** allow-list форматов, проверка сигнатуры файла, ограничение размера и потоковая запись. Пользовательские файлы лучше выдавать с отдельного домена/бакета, `Content-Disposition: attachment` и `X-Content-Type-Options: nosniff`.

### P2-6. Метрика популярности продуктов подделывается заголовком и не имеет срока хранения

**Где:** `backend/api/api_v1/product.py:52-60`, `backend/Services/product_analytics.py:10-20, 44-51`.

Для анонимного пользователя идентификатором просмотра становится произвольный клиентский `X-Forwarded-For`. Сервер не ограничивает этот заголовок доверенным proxy. Redis-ключи HyperLogLog и leaderboard не имеют TTL.

**Последствие:** любой клиент может искусственно поднять продукт в «популярных» и постепенно накапливать ключи Redis.

**Что сделать:** принимать forwarded headers только от доверенного proxy, использовать проверенный middleware/реальный IP, ограничить частоту и задать период хранения/агрегацию метрик.

### P2-7. Основной набор тестов красный из-за не обновлённого сценария ролей

**Где:** `backend/tests/api/api_v1/test_blocks_extensive.py:246-256`.

Запуск `pytest -x -q --ignore=tests/performance -k 'not test_download_pdf'` завершился так: `126 passed, 1 failed, 1 deselected`. Тест создаёт пользователя с ролью buyer и ждёт 200 от завершения блока. Новая политика намеренно запрещает покупателю доступ к курсам и отвечает 403.

**Последствие:** CI красный, а ложный тест маскирует следующие реальные регрессии.

**Что сделать:** заменить фикстуру на допустимую учебную роль (например, installer) и добавить отдельную проверку, что buyer получает 403. Не помечать CI как зелёный, пока полный набор не будет пройден.

### P2-8. Верификационный токен записывается в логи

**Где:** `backend/core/authentication/user_manager.py:107-123`.

Лог уровня warning содержит полный verification token. Любой, кто читает централизованные логи, получает действующий артефакт подтверждения email.

**Что сделать:** не логировать токены, пароли, DSN и заголовки авторизации. Для корреляции оставить user id и request id; существующие логи с токенами очистить/ограничить срок хранения.



### P3-2. CI проверяет только тесты и выдаёт много предупреждений

**Где:** `.github/workflows/ci.yml`, `pyproject.toml`.

CI запускает pytest, но не запускает linter, formatter, type-checker, coverage или security dependency scan. В уже прошедшей выборке есть deprecation warnings Pydantic и PytestCollectionWarning из-за ORM-классов `Test*`; они засоряют вывод и могут скрыть полезные предупреждения.

**Что сделать:** добавить Ruff (lint+format), mypy/pyright по мере готовности, coverage threshold, `pip-audit`/Dependabot и режим, при котором новые warnings не игнорируются. Переименовать импортируемые ORM классы в тестах через alias либо настроить collection так, чтобы предупреждений не было.

### P3-3. Дублируются измерения времени запроса

**Где:** `backend/middlewares/middlewares.py:20-53, 70-79`.

Один и тот же запрос измеряется дважды и получает `X-Process-Time` и `X-Process-Time-New-Again`. Это не уязвимость, но лишняя работа и неясный контракт API/наблюдаемости.

**Что сделать:** оставить один middleware и один документированный заголовок; внутренние метрики собирать без публичного раскрытия деталей производительности, если он не нужен клиенту.
