# Инструкция для агентов

## Назначение

Этот репозиторий содержит асинхронный backend-сервис Extra.
Сервис предоставляет REST API на FastAPI для пользователей, курсов, блоков, тестов, товаров, профиля, уведомлений и сертификатов.

Считайте текущий код источником истины.
`README.md` и `ARCHITECTURE.md` полезны как справка, но отдельные разделы могут отставать от кода.

## Стек

- Python 3.12 или новее.
- FastAPI и Uvicorn.
- SQLAlchemy 2 с асинхронными сессиями.
- PostgreSQL для рабочего окружения.
- SQLite in-memory для большинства тестов.
- Alembic для миграций.
- Redis для кэша.
- FastAPI Users для аутентификации.
- Jinja2 для HTML-шаблонов и писем.
- Poetry для зависимостей.
- Pytest и HTTPX для тестов.

Зависимости описаны в `pyproject.toml`.
`poetry.lock` фиксирует версии и должен обновляться вместе с изменениями зависимостей.

## Структура проекта

Все импорты backend рассчитаны на то, что каталог `backend` добавлен в `PYTHONPATH` или является текущим каталогом.

- `backend/main.py` создаёт приложение и запускает Uvicorn в режиме разработки.
- `backend/run_main.py` запускает приложение через Gunicorn.
- `backend/create_fastapi_app.py` содержит фабрику приложения, lifespan, middleware, Redis-кэш и админку.
- `backend/api/` содержит HTTP-роутеры и зависимости FastAPI.
- `backend/api/api_v1/` содержит API версии `v1`.
- `backend/Services/` содержит прикладную и бизнес-логику.
- `backend/Repository/` содержит запросы к базе данных и операции доступа к данным.
- `backend/core/models/` содержит модели SQLAlchemy и настройку базы данных.
- `backend/core/schemas/` содержит схемы Pydantic для запросов и ответов.
- `backend/core/authentication/` содержит настройку FastAPI Users и токенов.
- `backend/core/config.py` загружает настройки из переменных окружения.
- `backend/Domain/Enums/` содержит доменные перечисления.
- `backend/alembic/` содержит миграции базы данных.
- `backend/tests/` содержит интеграционные, функциональные и стресс-тесты.
- `backend/templates/` и `backend/mailing/` содержат HTML-шаблоны и отправку писем.
- `backend/middlewares/` содержит middleware приложения.
- `backend/admin/` содержит представления SQLAdmin.
- `ops/backup/` содержит скрипты резервного копирования PostgreSQL.
- `certificate/` содержит ресурсы HTML-сертификата.

В проекте нет каталога `backend/crud`.
Не создавайте такой слой без отдельной архитектурной причины.
Для новой прикладной логики используйте `Services`, а для запросов и записи данных используйте `Repository`.

## HTTP API

Общий префикс API: `/api/v1`.
Роутеры подключаются в `backend/api/api_v1/__init__.py`.

Основные группы API включают:

- auth
- users
- courses
- blocks
- tests
- certificates
- profile
- products
- product attributes
- terms
- FAQ
- search
- errors
- recommendations
- notifications
- messages
- backups

Swagger доступен по `/docs`.
ReDoc доступен по `/redoc`.

## Конфигурация и секреты

1. Скопируйте `backend/.env.template` в `backend/.env`.
2. Укажите рабочий URL PostgreSQL и секреты токенов.
3. Не добавляйте `backend/.env`, cookies, токены или пароли в Git.

Настройки используют префикс `APP_CONFIG__`.
Вложенные поля разделяются двойным подчёркиванием.
Например, URL базы данных задаётся через `APP_CONFIG__DB__URL`.

`backend/core/config.py` содержит значения по умолчанию и структуру настроек.
Не добавляйте секреты, URL окружений или параметры внешних сервисов прямо в код.

## Локальный запуск

Выполняйте команды из корня репозитория, если не указано иное.

```bash
poetry install --no-interaction --no-ansi --no-root
cp backend/.env.template backend/.env
docker compose up -d
```

Перед миграциями убедитесь, что PostgreSQL запущен и `backend/.env` содержит правильные значения.

```bash
cd backend
poetry run alembic upgrade head
poetry run python main.py
```

Для запуска через Gunicorn используйте `poetry run python run_main.py` из каталога `backend`.
Для проверки API откройте `http://localhost:8000/docs`.

## Миграции

Изменение модели SQLAlchemy обычно требует миграции Alembic.
Проверяйте миграцию на PostgreSQL.
SQLite-фикстуры тестов не заменяют проверку PostgreSQL-совместимости.

```bash
cd backend
poetry run alembic revision --autogenerate -m "describe the change"
poetry run alembic upgrade head
```

Проверяйте цепочку миграций и итоговую схему перед отправкой изменений.
Не редактируйте уже применённую миграцию без явной причины.

## Тесты

Основная команда запускается из корня:

```bash
PYTHONPATH=backend poetry run pytest backend/tests
```

Для одного набора тестов используйте, например:

```bash
PYTHONPATH=backend poetry run pytest backend/tests/api/api_v1/test_products.py -q
```

`backend/tests/conftest.py` создаёт SQLite-базу в памяти для каждого теста.
Фикстура также подменяет PostgreSQL-типы и функции поиска для SQLite.
Тесты API используют `httpx.AsyncClient` и переопределяют зависимость сессии базы данных.

При изменении бизнес-логики добавляйте тесты для обычного сценария, пустых данных, неверных входных данных, границ доступа и повторного вызова.
Не запускайте реальные внешние сервисы в модульных тестах.
Для Redis, PostgreSQL, почты и внешних HTTP-сервисов используйте фикстуры, подмены или отдельные интеграционные тесты.

## Правила разработки

- Сначала изучите связанные модели, схемы, сервисы, репозитории и тесты.
- Держите HTTP-слой тонким. Роутер должен разобрать запрос, вызвать прикладную логику и вернуть ответ.
- Не помещайте запросы к базе данных в роутеры, если их можно разместить в `Repository`.
- Не помещайте бизнес-правила в схемы Pydantic или middleware.
- Используйте `async` и `await` для операций с базой данных, Redis и HTTP.
- Передавайте `AsyncSession` явно через зависимости или параметры функций.
- Используйте типы для аргументов, возвращаемых значений и публичных структур.
- Используйте `pathlib.Path` для работы с путями.
- Не используйте глобальное изменяемое состояние без необходимости.
- Не дублируйте правила завершения блоков, тестов и курсов. Сначала найдите существующий сервис или helper.
- Сохраняйте обратную совместимость API, если задача не требует изменения контракта.
- Не меняйте имена полей ответа без проверки всех клиентов и тестов.
- Не удаляйте пользовательские изменения из рабочего дерева.

При работе с subprocess задавайте timeout, разделяйте stdout и stderr и проверяйте код возврата.
Генерируемые файлы и временные результаты сохраняйте в предназначенных для этого каталогах.
Не перезаписывайте исходные спецификации, миграции или пользовательские файлы без явной необходимости.

## Стиль кода

Соблюдайте PEP 8 и локальный стиль соседних файлов.
Используйте короткие функции с одной ответственностью.
Добавляйте docstring к публичным функциям, если функция сложная или имеет неочевидные ограничения.
Используйте имена `get_`, `create_`, `update_` и `delete_` для операций с сущностями.
Не добавляйте комментарии, которые повторяют код.
Комментарии должны объяснять причину решения или ограничение.

## Рабочий процесс агента

1. Проверьте `git status --short` и не затрагивайте чужие изменения.
2. Найдите существующий код и тесты для нужного сценария.
3. Сформулируйте минимальное изменение.
4. Реализуйте изменение в подходящем слое.
5. Добавьте или обновите тесты.
6. Запустите узкие тесты, затем полный релевантный набор.
7. Проверьте миграции, конфигурацию и формат изменённых файлов.
8. Повторно проверьте `git diff` и `git status --short`.

Перед завершением сообщите, какие файлы изменены, какие проверки выполнены и какие ограничения остались.
